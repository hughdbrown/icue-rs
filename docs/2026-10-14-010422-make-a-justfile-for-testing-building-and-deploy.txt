  Gaps that matter for widgets, most important first

  1. There is no plugin system at all (window.plugins.*). The shim sets every
     plugin<Module>_initialized flag to false and gives widgets nothing to call.
     Two things follow:
     - A widget can't open a link in the browser. The link provider is the
       simplest one in the spec (open a URL with the system browser), so it's a
       good first provider. It's also something the portfolio widget would use,
       e.g. clicking a ticker to open its page.
     - There's no sensor data. CPU/GPU temperature, load, power and memory
       widgets are the most common kind of iCUE widget, and none of them can
       work yet.
     - The plumbing that connects widget calls to Rust providers has to come
       before any provider. That's the right first piece of M3.
  2. There are no Rhai add-ins. Any custom data source (a homelab, game
     telemetry, etc.) currently has to be a web service the widget fetches over
     HTTP. That's how warthunder-hud reads localhost:8111. It works, but every
     new data source then needs its own HTTP server.
  3. The fetch proxy drops request headers. The developer guide says headers a
     widget sets are not passed on. Many APIs want the key in a header
     (Authorization, X-API-Key), so any widget for one of those APIs gets stuck.
     This is a small, self-contained fix.
  4. Permissions are declared, never approved. Every domain a manifest lists is
     allowed automatically, and nothing stops a widget from loading other
     domains directly from the page. That's fine for widgets you write yourself.
     It matters before you install third-party .icuewidget packages.
  5. There's no settings UI. Widget settings can only be changed with edgectl 
     layout set until the configurator host side is wired up. If you're planning
     widgets with many settings, this affects how pleasant they are to use.
  6. Touch is plain mouse events. Taps work. Multi-touch gestures (pinch, swipe
     between pages) don't, so for now widgets should be designed around taps and
     drags.
  7. EdgeHost doesn't start at login. There's no login item, so the dashboard
     has to be started by hand after a reboot.

  3. The sensors provider.

  it's cheap and unblocks API-key widgets. Rhai add-ins and permission approval
  can come after that.

⏺ Yes, they're configurable and ship separately from the EdgeHost binary. My
  last answer was confusing because iCUE uses the word "plugin" for something
  narrower, and I used it in iCUE's sense without saying so.

  Widgets and plugins are different things

  Widgets are what portfolio, piano and the War Thunder HUD are. Each is a
  folder (or a .icuewidget zip) with a manifest.json, index.html, scripts and
  styles. They:
  - ship separately from the EdgeHost binary;
  - are installed with edgectl install into ~/Library/Application 
    Support/EdgeHost/widgets/;
  - are placed and configured through layout.json, using their x-icue-property
    settings.

  That all works today. It was built in M1 and M2.

  Plugins (iCUE's term) are native data sources that a widget calls through
  window.plugins.<Name>. A web page can't read CPU temperature, the song that's
  playing, or a watched file by itself, so it asks a host-side provider. iCUE
  ships a fixed set: Sensors, Media, Link, FileSystem, Notifications, FPS,
  DeviceAction and StreamDeck. That bridge is what doesn't exist yet. The
  planned Rhai add-ins are your own providers of the same kind.

  So the gap I described affects widgets that need data a browser can't get. It
  doesn't affect whether you can write and ship widgets.

  Why your widgets work without plugins

  None of them asks for a plugin. Their manifests have no required_plugins:

  - Portfolio gets prices over HTTP from Yahoo Finance. It declares a url
    permission for query1.finance.yahoo.com, and EdgeHost's fetch proxy uses
    that to get around the browser's cross-origin block.
  - War Thunder HUD fetches localhost:8111, the game's own built-in web server,
    through the same permission mechanism.
  - Piano is plain HTML, JS and audio in the page. It needs no outside data.

  A plugin becomes necessary when the data has no HTTP endpoint, such as a
  CPU-temperature widget or a now-playing widget. For those, you'd have to write
  and run your own small HTTP server for the widget to fetch.

  The git widget

  There isn't one. examples/widgets/ has hello-edge, piano, portfolio and
  warthunder-hud. The installed store has those plus three Corsair or
  third-party ones (airquality, doodle-pad, robextourbillon). If someone has a
  git widget in progress, it isn't in this repo or the store yet.

  A git widget is a good example of the gap. A browser page can't run git or
  read .git/ on disk, so it would need one of these:
  - the FileSystem provider (planned for M3);
  - a Rhai add-in that runs git commands or reads repo state (also M3);
  - a separate local HTTP server that it fetches, the way War Thunder HUD does.
